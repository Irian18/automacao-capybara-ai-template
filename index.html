Automação E2E com Capybara, Ruby e IA

Template genérico de testes end-to-end com Self Healing Locators e RAG. Reduza a manutenção da suíte quando a UI muda e mantenha o histórico de alterações para análise.

📖 Sobre o projeto

Este é um template de automação de testes end-to-end (E2E) construído com Ruby, Cucumber, Capybara, SitePrism e Cuprite. Ele foi pensado para ser adaptado a qualquer aplicação web, oferecendo uma base sólida de BDD, Page Objects e relatórios.

O diferencial está nas camadas opcionais de inteligência artificial: Self Healing Locators, que corrige seletores automaticamente quando a interface muda, e RAG, que busca contexto nos Page Objects para enriquecer o prompt enviado ao modelo de IA.

O que o Self Healing faz? O Self Healing não substitui os step definitions. Ele atua dentro dos steps quando um locator quebra.

O que o RAG faz? O RAG fornece contexto adicional (como descrição de elementos das page objects) para o agente de Self Healing tomar decisões melhores. Ele também não substitui os step definitions.

O objetivo é reduzir a manutenção da suíte de testes, evitando falhas por mudanças de ID, classe ou estrutura do DOM, e ao mesmo tempo manter a confiabilidade dos testes com histórico de alterações.

Toda alteração de locator realizada pelo Self Healing é registrada em um histórico versionado. Isso permite que o time de QA revise manualmente cada mudança e verifique se o novo seletor realmente representa o mesmo elemento — evitando falsos negativos e mantendo a confiabilidade da suíte.

Por padrão, ambos os recursos estão desabilitados — basta usar os perfis cucumber -p self_healing e/ou cucumber -p rag quando quiser ativá-los.

📜 Histórico de alterações de locators

Cada vez que o Self Healing propõe um novo locator, a alteração é salva em features/support/self_healing/locator_history.json. Esse histórico funciona como um log de auditoria versionado: você pode verificar quando a mudança aconteceu, qual elemento foi afetado, qual era o seletor anterior e qual é o novo.

Isso é importante porque a IA, embora rápida, pode sugerir um seletor tecnicamente válido semanticamente diferente do original. Com o histórico, o QA pode revisar manualmente e decidir se aceita a correção ou se precisa ajustar o Page Object de forma mais segura.

O arquivo registra o page object, o nome do elemento, o motivo da alteração, o tipo de mudança (heal/manual) e a lista de versões do locator — como no exemplo abaixo:

Destaques do fluxo:

1️⃣ Execução normal primeiro

O teste executa da forma tradicional. A IA só é chamada quando realmente necessário, evitando chamadas desnecessárias à API e mantendo a execução rápida.

2️⃣ Falha como gatilho

Quando o Capybara não encontra o elemento, o Self Healing entra em ação, analisando a DOM atual para encontrar o melhor candidato de substituição.

3️⃣ Contexto com RAG

Se o perfil rag estiver ativo, o sistema busca trechos relevantes dos Page Objects existentes e os inclui no prompt, melhorando a qualidade da sugestão.

4️⃣ Auditoria automática

Toda sugestão é registrada no histórico com data, motivo, seletor antigo e novo, permitindo revisão manual antes de aplicar a mudança nos arquivos do projeto.

🚀 Como usar

Instale as dependências, configure o .env e execute os cenários com o perfil desejado. O projeto usa o cucumber.yml para combinar formatação, ambiente, drivers e relatórios.

# Instalar dependências bundle install # Copiar e configurar variáveis de ambiente cp .env.example .env # Edite o .env se for usar IA AI_API_KEY=sua-chave-aqui # Execução padrão (Self Healing e RAG desabilitados) bundle exec cucumber # Executar por tag bundle exec cucumber -t @login # Executar feature específica bundle exec cucumber features/specs/exemplo.feature # Apenas Self Healing habilitado bundle exec cucumber -p self_healing features/specs/self_healing/login_self_healing.feature # Self Healing + RAG habilitados bundle exec cucumber -p self_healing -p rag features/specs/self_healing/login_self_healing.feature # Executar instrução em linguagem natural via rake task bundle exec rake ai:run["Preencha o formulário de login"] # Executar cenários .feature de self healing via rake task bundle exec rake ai:run_features # Forçar re-descoberta de planos (ignora cache) AI_FORCE_RECORD=true bundle exec cucumber -p self_healing features/specs/self_healing/login_self_healing.feature # Gerar relatório Allure allure serve report/allure-results

Perfis principais disponíveis no cucumber.yml:

default

Perfil ativado automaticamente. Executa com Allure, Cuprite e Self Healing/RAG desabilitados.

self_healing

Habilita o agente de autocorreção de locators via IA e salva o histórico em JSON.

rag

Habilita a busca de contexto nos Page Objects para enriquecer o prompt da IA.

local / staging / sandbox

Definem qual arquivo de ambiente em features/support/environments/ será carregado.

🎛️ Perfis de execução

Os perfis do cucumber.yml permitem combinar rapidamente formato de saída, ambiente, driver e recursos de IA. Veja quando usar cada um:

| Perfil | O que habilita | Quando usar | |-----------------|----------------------------------------------|----------------------------------------| | default | Allure, Cuprite, ambiente example, sem IA | Execução diária e CI padrão | | self_healing | SELF_HEALING_ENABLED=true + LocatorHistory | UI instável ou em refactoring | | rag | RAG_ENABLED=true + índice de features/pages | Quer contexto dos Page Objects na IA | | local/staging | Carrega environment correspondente | Testar contra ambiente específico | | cuprite | Driver headless Chrome via CDP | Execução local rápida | | allure | Gera resultados para o Allure Report | Sempre que precisar de evidências |

⚙️ Processo de execução

Quando os perfis self_healing e/ou rag estão ativos, a execução segue fluxos bem definidos: o Self Healing trabalha no ciclo RECORD → REPLAY → HEAL, enquanto o RAG realiza indexação → recuperação → injeção de contexto.

Self Healing — RECORD / REPLAY / HEAL

│ 1. CARGA                                                                    │

                                 │
                                 ▼
┌─────────────────────────────────────────────────────────────────────────────┐

│    - O agente verifica se já existe um plano para a instrução               │
│    - Se não existir (ou AI_FORCE_RECORD=true), vai para RECORD              │
│    - Se existir, tenta REPLAY                                               │
└────────────────────────────────┬────────────────────────────────────────────┘
                                 │
                                 ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│ 3. RECORD                                                                   │
│    - Snapshot do HTML é capturado                                           │
│    - Se RAG estiver ativo, recupera contexto dos Page Objects reais         │

│    - Plano bem-sucedido é salvo em cache (PlanCache)                        │

                                 │
                                 ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│ 4. REPLAY                                                                   │
│    - Plano cacheado é executado sem chamada à LLM                           │
│    - Ferramentas rodam na ordem gravada                                     │
│    - Rápido e sem custo de API                                              │
└────────────────────────────────┬────────────────────────────────────────────┘
                                 │
                                 ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│ 5. HEAL                                                                     │
│    - Se REPLAY falha, identifica a ferramenta quebrada                      │
│    - Novo snapshot é tirado                                                 │
│    - Apenas o passo quebrado é enviado à LLM para correção                  │
│    - Plano cacheado é atualizado                                            │

🤔 Quando usar cada combinação

Self Healing e RAG trabalham juntos. O RAG é um contexto adicional para o Self Healing: você pode usar self_healing sozinho, mas se também usar rag, o agente consulta a base de conhecimento antes de gerar ou corrigir planos.

Nenhum recurso de IA

Use no dia a dia quando a aplicação está estável. A suíte executa mais rápido, sem chamadas externas à API de IA, e mantém o comportamento previsível.

bundle exec cucumber

Só Self Healing

Ideal durante refatorações de frontend, quando elementos mudam de ID, classe ou posição com frequência. O histórico registra cada correção para revisão posterior.

bundle exec cucumber -p self_healing

Self Healing + RAG

Melhor custo-benefício quando a aplicação muda e você quer sugestões de locators alinhadas ao padrão existente dos Page Objects. O contexto reduz alucinações da IA.

bundle exec cucumber -p self_healing -p rag

Só RAG

Não tem efeito prático sozinho, pois o agente de Self Healing não é carregado. Use sempre em conjunto com -p self_healing.

bundle exec cucumber -p self_healing -p rag

❓ Dúvidas comuns

A IA altera meus Page Objects automaticamente?

Não. O Self Healing salva as alterações propostas no histórico em JSON, mas não sobrescreve os arquivos .rb dos Page Objects. Você revisa e aplica manualmente.

O que acontece se a IA sugerir um locator errado?

O histórico mostra o seletor anterior e o novo, além do motivo da alteração. Isso permite identificar falsos positivos e corrigir o Page Object de forma segura.

Preciso de chave de IA para usar o projeto?

Apenas se for usar Self Healing ou RAG. A execução padrão do template funciona completamente sem API externa.

Posso usar Selenium em vez de Cuprite?

Sim. O projeto já prevê perfis de driver e pode ser configurado para usar Selenium WebDriver, Cuprite ou outro driver suportado pelo Capybara.
